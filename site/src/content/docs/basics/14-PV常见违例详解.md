# PV 常见违例详解：DRC / LVS / ERC 实操案例集

05 篇讲了物理验证在流程里干什么，本篇讲后端工程师每天实际面对的东西：**报错长什么样、为什么会出现、怎么改、什么时候可以忍**。

绝大多数初学者的痛点是：DRC 跑出来三千个错误，看着像洪水猛兽。实际上这些错误高度重复——按规则分类扫一遍会发现背后往往只有五六个根因，真正需要逐个动手的通常不超过十几处。

---

## 一、物理验证在流程里的位置和工具

```
布局布线完成 → stream out GDS/OASIS → Merge IP/Memory GDS → PV 工具跑 DRC/LVS/ERC
                                                             ↓
                                                      RVE / 结果查看工具
                                                             ↓
                                        修 ECO / 修版图 → 重跑 → 循环直到 clean
                                                             ↓
                                               Clean → LVS clean → tape-out
```

主流工具和对应场景：

| 工具 | 厂商 | 特点 |
| --- | --- | --- |
| Calibre | Siemens EDA | 事实标准，代工厂 rule deck 优先支持；nmDRC / nmLVS / PERC |
| IC Validator | Synopsys | 与 ICC2 / Fusion Compiler 集成好，分布式快 |
| Assura / Pegasus | Cadence | 与 Virtuoso 流程集成，模拟/定制电路常见 |
| PERC / Calibre PERC | Siemens EDA | 做 ERC / ESD / latch-up 专项可靠性 |

**重要认知：rule deck（也叫 runset）是代工厂给的，不是你写的。** 里面每一条规则有编号和代号，而同一条规则在不同工艺节点下的数值可能完全不一致。这些编号是我们后面 debug 的主要线索。

## 二、Runset 与结果查看：先培养正确的 debug 顺序

跑完 Calibre 之后，不要急于打开版图看，按这个顺序走：

1. **先看错误分类汇总**，而不是单个错误本身。Calibre 的 summary report 会列出每条 rule check 的结果与出错数量，据此锁定高频规则
2. **挑最高频的那几条**，通常处理掉前 3-5 类能消除 70-90% 的错误数量
3. **打开 RVE，用 `-hierarchy` 方式看**，找出错误集中在哪个 cell / 哪个 macro 边缘 / 哪个 instance
4. **确认"错误来源"是谁**：是自己 layout 的疏漏、是 standard cell 库本身带来的、是 IP/macro 周边的集成疏漏、还是代工厂 PDK 的已知 "false alarm"
5. **修之前先想 "同类/同一 root cause"**，避免一个个手点

```tcl
# Calibre DRC 典型调用
calibre -drc -hier /proj/pdk/t28/rules/calibre/drc/TSMC28HPC_DRC_.rsf
# 或者写在 runset 里submit
```

```tcl
# Innovus/Calibre 联调，直接把 DRC 结果推回 Innovus GUI
calibre -drc -hier runset_drc
# 结果用 Result Viewing Environment 打开
calibre -rve drc_results.db
```

## 三、DRC 高频违例：成因与修法

DRC 规则按物理本因可以归成几大类，每一类的修法是很不一样的。

### 3.1 宽度、间距类（最基础，也最常见）

**典型规则代号**：`M1.W.1`（金属 1 最小宽度）、`M2.S.1`（金属 2 最小间距）、`M3.S.2`

**现象**：两条平行的同一层金属走线挨得太近；或者某段金属（通常是绕线绕出来的 "角" 或 "细脖子"）比最小宽度还窄。

**常见成因**

| 原因 | 说明 |
| --- | --- |
| 布线工具的 track 走偏移 | 偏移量 off-grid routing 与 gridded rule 冲突 |
| 修 timing / SI 时手工走线 | 手工画的 path 偏离 preferred direction |
| 来自 Macro/IP 边界 | Memory 出 pin 位置和 standard cell 格点不同步 |
| 不同顶层 mask 版本 | stream out 时 unit / map 文件错漏，导致层映射偏移 |

**修法**

```tcl
# Innovus：先重跑 search & repair，工具能自己修掉大部分 spacing/width
routeOpt -wireOpt

# 如果还有残留：缩针对ians 区域做 ecoRoute
ecoRoute -target

# 最后手段：已经很接近 tapout，手工 route edit + 附近 track 改 friend wiring
editChangeVia ...
```

**关键判断**：如果同一类 spacing 错误在整 chip 均匀分布（不是集中在某几个 instance），八成是 **floorplan / track definition 与 PDK 不一致**，要修改 tech file / track definition，而不是点一个个 error。

### 3.2 End-of-Line Spacing（线头间距）

**典型规则代号**：`M2.S.3（EOL）`、`M3.EOLSP.1`

**现象**：一条线的末端和旁边线的侧面之间距离不足。这是 **光刻修正（OPC）在 90nm 以下必加的规则**——绕线末端在光刻过程中会有圆化效应，需要额外保护环境。

**成因 + 修法**

| 场景 | 修法 |
| --- | --- |
| 工具自动布线产生的孤立线头 | 打开布线的 EOL 优化选项，或后期用 `routeOpt` 自动处理 |
| Macro 出 pin 正对着 SRAM/相邻 macro 边界 | 调整 macro 位置或者加 routing blockage 限定走层 |
| 手工做的 power strap 分叉 | 修改 wire width / 增加分支长度让 EOL 精确满足 |

### 3.3 Via 相关（check lists 里非常高频）

**典型规则代号**：`V1.E.1`（Via1 包围，enclosure）、`V1.S.1`（Via-Via 间距）、`V2.A.1`（Via 面积）、`RV`（Redundant Via 规则，建议非必选）

Via 是 layer-stack 里最容易出错的位置，因为它涉及三层的几何关系：下层金属包没包住、上层金属包没包住、两个 via 挨太近。

**常见成因**

- **冗余通孔（Redundant Via）插入后**：工具叠了第二个 via 导致违例
- **个人 Diagnostic via array**：手工做 power strap 时自己拉的 via array 参数不对
- **DFM 阶段带了 density 检查**：某些区域 via density 不足（Via 数量规则要求）

**修法**

```tcl
# Innovus：让工具重新做 via insertion + 检查
setNanoRouteMode -routeWithViaPillar true
routeOpt -onlyViaOpt      ;# 只修 via 相关问题

# 工具补不明 optimal via:
addRedundantVias -viaRule default  ;# 注意不同 Node 可能有 VIAGEN 规则
verify_drc -limit 1000
```

**Redundant Via 的两难**：DFM 建议尽可能多的冗余通孔（提高良率），但 DRC 有时它又会引入 different class 问题。正确做法是先跑 `-droute`/`-via` optimization 让工具在 rule-clean 前提下最大化冗余 via 数量，而不是反过来。

### 3.4 最小面积（Minimum Area）

**典型规则代号**：`M1.A.1`、`M2.A.2`

**现象**：某段金属的**面积**小于规则要求，通常是布线留下了一小段孤立的岛状金属，或者是 fill exclusion 之后残留的碎片。

**成因**：布线工具在收尾阶段会做 metal patching，补丁太小就触发；另外 filler / decap / endcap 上那些很短的电源金属条也容易触发。

**修法**

```tcl
# 路由工具通常能自动把小的 metal piece 扩大到 min area
routeOpt -onlyMetalOpt

# 如果依然是几个，一般是在有 routing blockage 的区域 -> 检查是不是自己加的 blockages 覆盖了
```

### 3.5 金属密度（Metal Density / Window Density）

这是**后端工程师遇到最多的"非致命但必须解决"**的一类。

**典型规则代号**：`M1.DN.1`、`M2.DN.2`、`M3.DNW.2`（window density）

**为什么有这个规则**：CMP（化学机械抛光）过程中，如果某个区域金属太密集或太稀疏，抛光速率会不一样，导致表面不平整，进一步影响上层光刻的对焦深度。**这是纯制造需求，和电路功能完全无关**。

**规则的两个方向**

| 方向 | 含义 | 修法 |
| --- | --- | --- |
| Density too low | 某个窗口内金属量不够 | 自动填 dummy metal（不接任何 net 的浮空金属） |
| Density too high | 金属太密 | 拉宽 spacing / 修改 layout route；极端的要使 floorplan 改动 |

**修法：不要自己手画 dummy**

```tcl
# Calibre SmartFill 或者 ICV .Insert.Metal（跑在 signoff stage）
calibre -fill -hier runset_fill
# 之后必须重跑：fill 会改变寄生参数 -> 需要重新抽取 -> 重新 STA
```

> **这是 PV 里最大的坑**：dummy fill 会改变金属的耦合电容，改变了寄生参数，进而改变时序。完整正确的流程是：**stream out → fill → 重新抽取寄生 → 重跑 STA → 确认 timing 依然收敛 → 再做 final DRC/LVS**。如果你们团队跳过了 "fill 后重跑 STA"，芯片拿回来跑不达标不要奇怪。

### 3.6 天线效应（Process Antenna）

**典型规则代号**：`M2.ANT.2`、`ANTENNA.GATE`（antenna ratio 计算）

**原理**：制造过程中，金属层是一层层淀积并刻蚀的。在刻蚀某一层金属时，已经连到栅极上的、**正在被刻蚀的长金属**会像天线一样收集等离子体的电荷，电荷积累到一定程度会击穿薄栅氧。

```
   长长的 Metal2（面积 A_M2）
        |
        v
    ----栅极（面积 A_gate）  ← 如果 A_M2 / A_gate > 规则上限，则 Plasma damage risk
```

**修法三选一**

| 方法 | 做法 | 代价 |
| --- | --- | --- |
| 跳线（Metal Jump） | 断开长金属，往上跳一层再绕回来，使单次刻蚀时连到栅上的面积变小 | 占用上层绕线资源 |
| 反偏二极管（Antenna Diode） | 在受影响的 gate 附近插入 NAC / diode cell，提供电荷泄放路径 | 面积 + 少量漏电 |
| 增大 buffer 驱动以获得更大 gate area | 通过 upsize driver 拉大分子分母里的分母 | 面积 + timing 变化 |

**现代工具可以在布线阶段自动处理：Innovus 里通过 `setNanoRouteMode` 指定天线二极管单元名，布线时自动插入，不必等到 Sign-off 阶段手工补。

### 3.7 Well / Tap 相关

**典型规则代号**：`NW.S.1`（Nwell 间距）、`TAP.D.1`（Tap cell 到某 device 的距离）、`PP/NP.S`（注入层间距）

- **Tap cell 距离规则**：任何一个 MOS 管的衬底/井都需要电位接触，距离 Tap 过远会导致 latch-up 风险（见下面 latch-up 部分）
- **Nwell 间距**：相邻两个不同电位的 Nwell 需要足够间距；**同电位的 Nwell 通常允许更近甚至可以合并**，所以规则里有 `same potential` 判定分支
- **未举例情况**：部分工艺使用 tapless library，此时 n/p well tapping 由 Tap/EndCap cell 完成，缺失会出现大量此类 DRC。检查方法：`verifyWellTap` / `checkTapDensity`

### 3.8 Latch-up 相关（DFM / ERC 里也查）

**典型规则代号**：`CLUP.*`（Calibre PERC latch-up check）

物理成因是 CMOS 结构里寄生的 NPN / PNP 双极管形成正反馈的可控硅（SCR）结构。防护准则本质上是两条：

1. **每个井到 power/ground rail 的电阻要足够小** → 这意味着 tap 要密、要走 approached tap rule
2. **注入的载流子要能被及时收集** → 规则上通常表现为 tap 到敏感器件（IO device、高摆幅节点）的距离约束

```tcl
# Innovus 插入 tap cell / endcap
setEndCapMode -reset
setEndCapMode -boundary_tap true
addEndCap

# 检查 tap 覆盖率
verifyWellTap -report tap.rpt
```

### 3.9 Boundary / scribe line 类

划片道（scribe line）、seal ring 相关的 DRC 一般不会在自动配置里触发，出问题通常是在**整体 merge foundry IP / IO ring 之后**。常见错误：

| 问题 | 表现 |
| --- | --- |
| seal ring 与内部顶层金属距离违规 | 涉及 crack-stop / 掺杂边界规则 |
| IO pad 与内部高压器件的间距 | 高压专属间距规则 |
| 对位标记（alignment mark）区域被覆盖 | 这些区域必须留空，不能摆放任何单元或金属 |

### 3.10 常见的 "假错" 与 Waiver

有几类报错不需要修改版图，而是走 waiver（豁免）流程：

- **代工厂 rule deck 已知 bug**：部分 SVRF 在某些条件下的 false positive，代工厂会发 errata
- **标准库/IO 库自带的 DRC clean waiver**：提供商承诺其 GDS 层次在集成上下文里 clean，这时需要合并 waiver file
- **器件 datasheet 明确允许的特例**：比如某些 MIM 电容相关的结构天然低于最小宽度，但属于规则文档认可的例外

**Waiver 的正确姿势**：不要直接删除错误，要用 `-waive` 机制留下审计记录，而且要针对**已知 rule + 具体 cell / 具体 window**，不能用大范围筛选掩盖问题。

## 四、LVS：常见的十大错误与排查顺序

LVS 的本质是把**版图提取（extract）出来的网表**和**源网表（source netlist，一般是综合出来的 Verilog 或者 CDL）**做拓扑比对。它在流程里不可跳——一个 LVS fail 意味着电路连错，可能是芯片ailroad。

### 4.1 标准 Debug 流程

```
1. 看 rep file 顶层的 "Comparison Result:" — 先定方向：instance/port/net/parameter 哪一类不匹配
2. 如果是 connectivity error -> 看 lvs.rep 里的 "Incorrect Instances" / "Incorrect Nets"
3. 如果是 extraction issue -> 先确认 device recognition layer 都用上了，看 extraction summary 里的 device count
4. 如果是 power/ground -> 先做 "short isolation" 查 VDD/VSS short 或 open
5. 用 RVE 的 cross-probing 定位到具体坐标
```

### 4.2 十大常见错误表

| 错误 | 报错常见字段 | 典型成因 | 处理方式 |
| --- | --- | --- | --- |
| Short | `two or more ports...short` | 版图里出现了非预期的短接：可能是绕线、dummy fill 或者电源短条把两个不同 net 连在一起 | 用 RVE 高亮定位到具体层，确认是 merge 偏移、还是 fill 规则需要调整 |
| Open | `net missing instance` / `open net` | 少了通孔；或者电源轨没有连到单元的电源脚 | 用 `verifyConnectivity` 查 PG 完整性，重点检查对应层的 via 是否缺失 |
| Port missing | `port missing from layout` | 源网表里的端口在版图中找不到对应标注：多半是缺 text label，也可能是 power/ground 端口没有声明 | 检查 label 层是否落在对应的金属 drawing 上；检查 LVS 的 power/ground 名称是否与网表一致 |
| Incorrect instance | Cell port 数量/名称不匹配 | LVS netlist 用的 std cell CDL 版本与 layout SCH 不一致 | 统一 `source.add.cdl` 与 Calibre 用的库版本 |
| Device parameter mismatch | `W` / `L` mismatch | 版图提取出的器件宽长与网表定义不一致，常见于不同版本的 pcell 或 bin 划分不同 | 统一两边的库版本，或调整提取时的器件识别精度 |
| Unmatched (extra) device | `unmatched devices: layout vs source` 数量不等 | layout 有额外 device（可能是 TIE cell/dummy，也可能 DC layer 出错） | 检查 DC/spare cell、检查 filler/decap 是否被识别为 device |
| Empty extraction | device count = 0 | 一个器件都没提取出来，通常是 layer map 没生效，或 stream out 的层次映射文件版本不对 | 检查 layer map 文件与 stream out map file 是否匹配当前工艺版本 |
| Black box | `black box cell found` | 引用的 library box 没有 CDL /gds；IP 提供 incomplete file | 向 IP vendor 索取完整 LVS netlist |
| Soft connect | 连接被认为是弱连接或 tie | 存在只能通过高阻路径到达的节点，比如浮空的输入脚 | 检查 tie cell 是否真正连上，必要时开启 `LVS SOFTCHK` 做弱连接检查 |
| Filter / Reduce error | 器件被错误合并或精简 | 并联 / 串联 MOS 在不该合并时被合并，或反之 | 检查 LVS 的 REDUCE 设置与 parallel / series 器件处理选项 |

### 4.3 三个实战中最耗时的坑

**坑 1：数字dummy / spare gate 导致 device 数量不等**

数字后端为了 ECO 方便会插入 spare cell（tie-off 输入的空逻辑门）或者 tie-high/tie-low cell。这些 cell 在 source netlist 里没有、在 layout 里有。如果不做处理，LVS 会在器件比对阶段报出大量 unmatched device。

```tcl
# 解决方法一：LVS box 或 exclude cell
LVS BOX <tie_cell_name>
# 解决方法二：Box 掉整个 filler / decap / tap / endcap
LVS FILTER <celltype> OPEN
```

**坑 2：PG short 在 full-chip merge 的 macro 边界**

相邻两颗 memory 的电源轨与顶层电源条的对齐偏差，会让同一个电源网络在 merge 后被识别成两个不同的 net，从而比对失败。

排查方法是分层来做：先跑 sub-block LVS 确认每个模块本身干净，再做 full-chip。大量 full-chip 报错的根因其实在某个子模块里。

**坑 3：Text/Label 层缺失导致 Port 识别失败**

端口识别失败是最容易卡人的一类：版图里 pin 的形状是对的、电气连接也通，但 LVS 就是报 missing port。绝大多数情况是 text label 没落上去。检查方法：

```
Calibre rule: TEXT LAYER <n> ATTACH <layer>
确认 stream out 的时候 include text layer, 且 label 落在 pin 金属层范围内
```

## 五、ERC：可靠性检查

ERC 检查电气规则，典型的几类：

| 检查项 | 含义 | 常见 fail 原因 |
| --- | --- | --- |
| Floating gate | 栅极浮空，电位不定，会导致漏电甚至击穿 | tie cell 缺失、ECO 时忘了把 input 接到 tie |
| Floating well | 井没有电位接触 -> latch-up 风险 | tap cell 密度不足、macro 边缘忘了加 tap |
| Multiple driver | 同一个 net 被多个 driver 驱动 | scan 或者 UPF cell 冲突、ECO 短接线弄错 |
| Diode / ESD path | ESD 泄放路径是否完整 | IO ring 上 ESD device 及 wiring 缺失 |
| Device at extreme voltage | 器件的衬底或源端电位超出工艺允许范围 | 多电压域或 power gating 中选错了单元类型 |
| Signal electromigration | 电流密度超过线宽允许上限 | 电源条或时钟线过细、扇出过大 |

浮空栅在数字设计里特别容易出现：spare cell、未连接的输入脚动辄成千上万个，必须靠系统性检查而不是肉眼看：

```tcl
# Innovus：检查浮空输入管脚
checkFloatingPin
# 或者设置自动 tie-off 的最大扇出
setTieHiLoMode -maxFanout 8
```

## 六、天线效应与密度的修复：一个完整流程

把上面几块串起来，看一个完整的签核流程：

```tcl
# ========== 标准 Sign-off PV 流程 ==========
# Step 1: 布线后自查
verify_drc -limit 2000
verifyProcessAntenna

# Step 2: stream out
streamOut results/top.gds -mapFile streamOut.map -libName DesignLib \
    -units 2000 -mode ALL

# Step 3: Calibre DRC / Antenna 修复
calibre -drc -hier runset_drc
calibre -rve results_drc

# Step 4: Metal fill (含 antenna-aware fill option)
calibre -fill -hier runset_fill

# Step 5: 重抽寄生 -> 重跑 STA (关键！)
# StarRC / QRC extraction on the filled GDS
starrc -cmd extract.tcl
# PrimeTime STA with new SPEF

# Step 6: final LVS/DRC clean check
calibre -lvs -hier runset_lvs
```

**Step 5 恰恰是最容易被省略的一环**。如果 post-fill 的 STA 出现了新的时序违例，就要回到 Step 1 重新调整布线，而不是带着违例出片。

## 七、面试五问

**Q1：为什么 DRC 里有 metal density 规则？超标会怎样？**

答：CMP 抛光过程中，金属密度不均会导致抛光速率不一致、表面不平整，进一步影响上层光刻的焦深。密度不足用 dummy metal fill 补齐（Calibre SmartFill），但要留意 fill 会改变寄生参数，必须重抽 SPEF 重跑 STA。

**Q2：天线效应是什么，怎么修？**

答：制造时刻蚀金属的过程中，连到栅氧上的长金属会像天线一样收集电荷，可能击穿栅氧。三种修法：金属跳线（断开长金属，跳到上层再绕回来）、在受影响的 gate 上挂反偏二极管（提供泄放路径）、把 driver upsize 以增大栅面积从而降低 ratio。

**Q3：LVS 报 "incorrect net / short"，你怎么定位？**

答：先看 summary 判断属于 connectivity 还是 extraction 问题。如果是 short，用 RVE 高亮 highlight 到具体坐标层。经验上是分层排查：先跑 sub-block LVS，如果每个 block 都干净、merge 后才失败，问题多半出在顶层电源条或者 macro 边界的对齐偏差上。

**Q4：什么是 spurious device 导致的 LVS 数量不匹配？怎么处理？**

答：spare cell、tie cell、tap/filler/decap 在 layout 里有物理 device 但 source netlist 里不带。用 `LVS FILTER` 或 `LVS BOX` 把这些 cell 类型框起来不参与比对，而不是从 netlist 里删单元。

**Q5：fill 之后为什么必须重跑 STA？**

答：dummy metal 会改变邻近互连线的耦合电容，寄生参数会变。如果只追求一次 DRC clean 就直接 tape-out，实际硅片的时序会偏离签核时的结果，严重的会跑不到目标频率。

## 小结

物理验证不是"跑完工具点点错误"那么简单。它的本质是把代工厂几十页语焉不详的工艺限制，转化成可以被机器逐条校验的规则。DRC 保证几何可制造，LVS 保证拓扑逻辑正确，ERC 保证长期可靠。

真正拉开工程师差距的地方，是能否从 report 的汇总里看出规律：几千条报错背后往往只有五六个根因，而不是逐个去点。

# 功耗分析实操：从 PrimeTime PX 到 Voltus 的完整链路

06 篇讲了 UPF 电源意图怎么写，本篇讲另一件事：**写完了怎么算，算出来怎么查，查出来怎么降**。

功耗分析和时序分析有个本质区别：时序是**静态可判定的**（给定库和约束，路径延时是确定的），功耗是**依赖于激励的**（同一颗芯片跑视频解码和跑待机，功耗能差 5 倍）。这个区别导致了功耗分析在工程上有一整套时序分析没有的麻烦：活动率从哪来、时间窗取多长、精度和资源怎么权衡。

---

## 一、功耗的三项构成

先记下这个公式，后面所有分析、报告、降功耗手段都能归类到其中一项：

```
P_total = P_switching + P_internal + P_leakage

P_switching = 1/2 × C_load × VDD² × f × α      （对负载电容充放电）
P_internal  = Q_sc × VDD × f × α + P_glitch   （PMOS/NMOS 同时导通的短路电流 + 毛刺功耗）
P_leakage   = I_sub × VDD + I_gate × VDD       （亚阈值漏电 + 栅漏电）
```

关键点：

| 项 | 与什么成正比 | 降它有啥招 |
| --- | --- | --- |
| P_switching | 负载电容 C、频率 f、翻转率 α、**VDD 的平方** | 降 VDD 收益最大（平方关系）、clock gating 降 α、减小 fanout 降 C |
| P_internal | 翻转率 α、输入 slew | 减小 input slew、balance rise/fall arrival、消除毛刺 |
| P_leakage | 单元面积 × 器件数、VT 类型、温度（指数） | 用 HVT/SVT cell、power gating、减少 device count |

**为什么 VDD 那么香**：功耗和 VDD 平方成正比，电压降 10% 功耗降 19%。这也是为什么 DVFS、多电压域（Multi-VDD）是降功耗最有效的手段——代价是电平转换器的面积和时序开销。

**漏电的温度指数关系**： leakage 大致随温度每升高 10°C 翻一倍。这是芯片热失控的物理根源，也是 Sign-off 必须在 **worst case 温度 + worst case process（fast-fast / low VT）** 下做 static IR/leakage 分析的原因。

## 二、三条分析技术路线

工程上按「设计阶段 → 可获得的数据」来选工具，形成三级火箭：

| 阶段 | 输入 | 工具 | 精度 vs PTPX(Gate+脱敏 VCD) | 单点耗时 |
| --- | --- | --- | --- | --- |
| RTL Early | RTL + 大致 toggle | Joules / PowerArtist / SpyGlass Power | ±30% ~ ±50% | 小时级 |
| Gate-Level Vectorless | 综合后网表 + 默认活动 | PrimeTime PX (默认模式) | ±50% ~ 完全失真 | 分钟级 |
| Gate-Level VCD-based | 布线后网表 + SPEF + 后仿 VCD | PrimeTime PX / Voltus | ±5% ~ ±15% | 天级 |
| 版图级 IR Drop | DEF + SPEF + 电源网 + VCD | Voltus / RedHawk | ±10% | 天级 |

**第一级 ROI 最高**：RTL 阶段一次 power intent 修改能省 30% 功耗，流片后再想改就是 Metal-Only ECO 或者重来。所以成熟团队的策略是 **RTL 阶段用 Joules 每天 regression 出功耗趋势线**，把 gate-level PTPX 留到 Sign-off 做精确确认。

> 注意「Vectorless」这个词的误导性：它不是"不需要激励"，而是"用工具默认的、统计意义上的活动率"（比如每个 register 输出翻转率 0.1，primary input 0.25）。这种分析结果只能用来**比较相对大小**（哪个模块最耗电），绝对数字没有参考价值，面试时把这两者混为一谈会被追问。

## 三、PrimeTime PX 实操

### 3.1 输入清单

一次可信的 PTPX 分析需要准备齐这些：

| 文件 | 格式 | 说明 |
| --- | --- | --- |
| 门级网表 | .v / .ddc | 最好是布线后回注的网表，含实际 cell 类型 |
| 时序库 | .db | **必须含功耗信息**：CCS (Composite Current Source) 或 NLPM。没有 power data 的 lib 会报 `PWR-XXX` 警告并退化成估算 |
| 寄生参数 | .spef / .sbpf | 必须读！没读 SPEF 的 switching power 会显著偏低且不随布线变化 |
| 约束 | .sdc | 时钟、case analysis、false path 都会影响 propagated activity |
| 活动率 | .vcd / .saif / SAIF-RTL | 仿真产生的翻转波形，分析精度的天花板 |
| 电源意图 | .upf | 只在多电压域设计里必需 |

### 3.2 典型脚本

```tcl
# ============================================================
# PrimeTime PX 功耗分析模板
# ============================================================

# --- 1. 库与网表 ---
set link_path "* /proj/pdk/t28hpc/ccs.db /proj/pdk/t28hpc/io.db"
read_verilog   ./results/pnr_routed.v
current_design top
link_design
read_sdc       ./constraints/top_func_wc.sdc
read_parasitics -format spef ./results/top.spef.gz

# --- 2. 电源网络 / 多电压域 ---
read_upf ./upf/top.upf          ;# 有 UPF 时优先；没有则手工 set_voltage
set_voltage 0.90 -object_list VDD_CORE
set_voltage 1.80 -object_list VDD_IO

# --- 3. 分析模式 ---
# time_based: 按时间窗积分，精度高，慢
# averaged:   用翻转率反算平均功耗，快，丢失瞬时峰值和 glitch
set_power_analysis_mode \
    -analysis_type time_based \
    -waveform_interval 10 \
    -waveform_format fsdb \
    -waveform_output ./results/power_wave \
    -time_window {100000 200000}
```

这里有几个参数常被念错：

- `-waveform_interval 10`：每 10ns 采一个功耗点。太小会使输出文件爆炸（几 GB），太大则丢失瞬态峰值。对典型的 500MHz ~ 1GHz 设计，取时钟周期的 5 ~ 20 倍比较合理
- `-waveform_output`：生成 FSDB 功耗波形。很多人不知道这个开关，用了 averaged 模式然后问"我的峰值功耗怎么测"——PTPX 本身不支持巅峰功耗分析，它是 **cycle-average（数十~数百个周期内的平均）**
- `-time_window {start end}`：仿真波形的哪一段参与分析。**这是工程上最容易出错的一步**，下面详说

### 3.3 矢量读取与反标

```tcl
# VCD：信息完整，含 glitch / X 传播，文件大
read_vcd -strip_path tb_top/dut ./sim/video_decoder.vcd.gz
# SAIF：压缩格式，文件小，丢失 glitch 精细结构
read_saif -strip_path tb_top/dut ./sim/video_decoder.saif

# 若仍有未被反标覆盖的信号，用默认活动率兜底
set_switching_activity -toggle_rate 0.05 -static_probability 0.5 \
    [get_nets -hier unclocked_*]

update_power
```

> `-strip_path` 是 90% 的初学者报错来源。VCD 里的 hierarchy 是 `tb_top.dut.xxx`，而 netlist 里是 `top/xxx`，路径对不上会导致大量 net 报告 "no activity specified"，工具自动用默认值。这时候功耗报告的数字不是"错的"，是"基于假设的"，很难被发现。

## 四、VCD 与 SAIF：选哪个

这是面试高频题，也是一个真正的工程权衡：

| 维度 | VCD | SAIF |
| --- | --- | --- |
| 是否含 glitch（毛刺） | 是 | 否（只存 toggle count / duty，丢失时序细节） |
| 文件大小（典型 100 万 gate 设计跑 10 万周期） | 数十 GB | 数百 MB |
| 含 X 传播信息 | 是 | 否 |
| 何时用 | Sign-off、glitch power 重要时 | 整 chip regression、早期 |

**工程上的派生问题**：如果用 SAIF 而设计又有明显的 glitch（比如某些 组合逻辑深度大、输入到达时间严重不平衡的乘法器或者未打拍的组合云），SAIF 会把这部分功耗完全漏掉，报告出来比实际低 5% ~ 25%。这种情况下转换 VCD 变成 SAIF 是错的，应该用 VCD。

**X propagation 隐藏陷阱**：VCD 里有 X 意味着 known in simulation but unknown in analysis。工具处理 X 有几种策略：

```tcl
set_power_analysis_mode -sequential_method THREE_POINT   ;# 默认，最保守
# 或用 zero delay 推算活动率，快但偏乐观
```

当 VCD 有大量 X 传播时，实际功耗往往偏乐观。如果 X 占比超过 15% 建议回去查仿真激励，不要直接拿来分析。

## 五、时间窗怎么选

这是 PTPX 分析里最不被重视、但对结果影响最大的一环。

**错误做法**：跑完仿真，取整个 VCD。

典型的 SoC 仿真波形里包含了：复位序列、PLL 锁定等待、DMA 初始化、然后是真正的工作负载。如果取全时段平均，前面那堆近乎静止的低功耗阶段会把真实负载的功耗拉低。

**正确做法**：

1. 先用 VCD 自己画个活动率趋势图（或者用 `-waveform_output` 输出的 fsdb 功耗波形）
2. 找到稳态区间（典型 workloads 反复执行、没有初始化活动那段）
3. 窗口至少覆盖 **一个完整的最慢工作循环**（比如视频解码的一帧 + 后续 P 帧）
4. 窗口长度一般取 **1000 ~ 100000 个时钟周期**

```tcl
# 反例：直接读整个 VCD，包含了 reset 与配置初始化的低功耗段
set_power_analysis_mode -analysis_type time_based

# 正例：限定在稳定 workload 区间
set_power_analysis_mode \
    -analysis_type time_based \
    -time_window {1500000 3500000}   ;# 2M 个 ns 的稳定负载
```

**多条应用场景要分开**：一个手机 SoC 至少有「视频播放」「游戏」「待机」「通话」四个功耗 profile。正确做法是生成 4 份不同的 VCD，分别跑 PTPX，最终在 spreadsheet 里用使用场景占比加权得到预期续航。这块工作通常是系统组而不是后端组负责，但后端需要被告知**应该用哪个 profile 做 Sign-off**。

## 六、常见的六类分析错误

### 6.1 忘了读 SPEF

症状：switching power 偏低 20% ~ 40%，且布局布线前后两次结果几乎一样（因为同一个网表的线负载估算没变）。

验证：Compare the reports 的 `Net Switching Power` 项，正常应该在 hierarchical 分析里有单独的 Net 明细行。

### 6.2 Liberty 没有 CCS/ccsn 模型

症状：internal power 明显失真，且 glitch power 完全缺失。旧的 NLDM-style 查表（七点 model）只在 input slew / output load 二维表上查 energy，不能表达 Cswitching current waveform。

检查方法：

```tcl
check_power   ;# PTPX 会明确报告哪些 cell 缺少 CCS /何处用了 NLPM fallback
```

### 6.3 VCD 时间窗包含初始化

见上一节。典型现象是报告数字很漂亮，芯片上板却发烫。

### 6.4 忘记 case analysis / false path

当你在 SDC 里设了 `set_case_analysis 0 [get_ports test_mode]`，工具会认为受该信号控制的下游逻辑输出不翻转，进而把这部分 net 的动态功耗按零计算——这是正确的。反过来，如果该设而没设，工具会退回默认活动率，把本该关闭的模块按正常翻转计算，报告明显高于实测。

反之亦然：不要把 `set_case_analysis` 误用到真实存在多种工作模式、并且该引脚确实会翻转的设计上，否则会把本应耗电的模块按零功耗计算。

### 6.5 Clock Gating 单元的 enable 推断

一个经常被忽略的细节：ICG 单元输出端的 net activity 取决于 gating 后的 enable waveform，而不是 clock 本身的 toggle。

```tcl
# 让工具用 enable 逻辑推断 gated clock 的活动率，而不是默认 100% toggle
set_power_analysis_mode -enable_clock_gating_analysis true
```

如果这个开关没开，所有 gated domain 的下游 logic 会被按完整 toggle 算，报告会比实测高。

### 6.6 多电压域的 supply set 有效性

```tcl
check_mv_design -power_nets       ;# 检查所有 Instance 是否有有效 supply set
report_power_domain -verbose      ;# 检查 domain hierarchy 是否如预期
```

如果某个 domain 的电压关联错了（比如 0.9V 的域按 1.0V 算），功耗会因为平方关系偏离约 23%。

## 七、怎么读功耗报告

`report_power` 的默认输出是总分，实际调试时要用这几个命令分解：

```tcl
# 按 hierarchy 层级看，一眼看出哪个模块最耗电
report_power -hierarchy -levels 3

# 按 cell type 分类看：register / combinational / clock network / macro
report_power -by_cell_type

# 只看某个模块
report_power -include_only [get_cells -hier *video_dec*]

# 存档报告，用于回归跟踪
report_power -nosplit > rpts/power_summary.rpt
```

**经验：一个典型的 mobile SoC core 里，时钟网络功耗占总功耗的 30%~45%。** 如果报告显示 clock network 只占 10%，大概率是时钟树没识别好：CTS 没做，或者网表里插入的 clock buffer/inverter 没有被工具判定为时序单元的下游负载。

**层级分析的另一个用法**：如果某个模块的寄存器功耗异常偏高，先查是不是约束疏漏——一堆触发器挂在同一个常开时钟上，却没有对应的门控使能。

## 八、从报告到降功耗 ECO

拿到 report 后通常按这个优先级推进：

1. **确认 Cost Benefit：目标是多少 mW / 要降百分之几**。如果只是 5% 以内，通常靠小而精的模式 (HVT cell swap) 解决，不必动架构
2. **Clock gating 有效性检查**：Lint 出 should-have-been-gated registers
   ```tcl
   # 用 SpyGlass / PowerArtist 找出没有 clock gating 的 register bank
   # 或者在 PTPX 里对比 gated / ungated 的活动率
   ```
3. **HVT / SVT cell swap**：slack 有裕度的地方把 LVT 换成 HVT，static leakage 降 30% ~ 70%，路径延时增加 15% ~ 30%
4. **Power gating 有效性验证**：基于 retiring check 和 isolation status
5. **毛刺消除**：平衡多路输入的到达时间，或者在深度组合逻辑中插入流水寄存器

不要一上来就做 power gating —— 孤岛 implementation 的验证代价远超 5% 的 leakage 收益，只有在 RTL 阶段就把上下电序列、隔离策略规划清楚的设计才适合。

## 九、版图<｜hy_place▁holder▁no▁813｜> Voltus / RedHawk：IR Drop 联动

门级 PTPX 算出的每个 instance 功耗，会被 IR Drop 工具换算成随时间变化的电流源，喂给电源网 RC 网络：

```
Instance  current(t)  --->  电源网提取 RC  --->  每个 Instance 上的 VDD 实际值
                                                ↓
 Instance VDD drop > 5~10%  →  cell delay 增大 → timing degradation → DynamicIR aware STA
```

这里有个闭环：**IR Drop 会让 cell delay 变大，delay 变大会让 transition 变慢，transition 慢会增加 internal power，进而加大 IR Drop**。这个正反馈在电源网偏弱、利用率过高的设计里会被放大，所以 RedHawk / Voltus 提供 `-dynamic_current` 模式（把 PTPX 输出的 fsdb 波形直接 push 到 IR 引擎）而不是传统的 static average。

工程实践：只有当 IR-aware STA 的 timing degradation 超过 30~40ps 时才需要挨个 virtual rail 去削减峰值——过早虚拟压降修电源网，成本远高于收益。

## 十、面试五问

**Q1：PTPX 分析的必备输入有哪些？缺了 SPEF 会怎样？**
答：网表、带 power model 的 liberty、SDC、parasitics、活动率文件（VCD / SAIF），多电压域设计还需要 UPF。缺 SPEF 会导致线网的动态功耗被严重低估，而且布局布线前后结果几乎不变，很容易被误认为"设计本身没问题"。

**Q2：VCD 和 SAIF 的区别？什么时候必须用 VCD？**
答：VCD 保留完整时序和 glitch 信息，SAIF 只存 toggle count / duty cycle。当 glitch power 占比大（比如 组合逻辑深度大、毛刺明显的乘法器或移位链）或者需要分析 X 态传播对活动率的影响时必须用 VCD。

**Q3：峰值功耗 PTPX 能算吗？**
答：不能。PTPX 是几十到几百 cycle 的 averaging engine，无法表达 nanosecond 级别的 transient peak。纳秒级峰值要交给带逐 cycle 电流波形的 Voltus / RedHawk 处理。

**Q4：为什么降功耗最有效的手法是降电压？**
答：Dynamic power 与 VDD 平方成正比。降 10% VDD 降 19% 动态功耗，前提是时序上要有相应裕度，且要重跑全部 corner 确认没有因此产生新的违例。

**Q5：leakage 随温度怎么变？**
答：大致每升高 10°C 翻倍（亚阈值电流指数依赖），这也是 thermal runaway 的物理根源。所以 static leakage Sign-off 要在 worst-case temperature corner 做。

## 小结

PTPX 分析的分水岭不在于会不会写脚本，而在于**知道自己的数字为什么可能是错的**：SPEF 读没读、lib 有没有 CCS、VCD 窗口取对没有、case analysis 设没设、gating 分析开关开没开。这五项检查做下来，报告的数字才可以在 review 时拿出来说话。

# 八股题库 · 03 面积与拥塞

> **数字 IC 后端面试必考**。这两个话题决定了设计能否 tapeout——面积定成本，拥塞定布线可达性。
> 本专题 12 道题，覆盖 Utilization、Macro Placement、Congestion Map、Routing Shortage、CR 等核心概念。

---

## 一、核心概念速查

### 1.1 Utilization（利用率）

| 项 | 含义 | 公式 |
|---|---|---|
| **Core Utilization** | 标准单元面积 / 可用面积 | `Standard Cell Area / Core Area` |
| **Floorplan Utilization** | 含宏单元总占用 | `(StdCell Area + Macro Area) / Core Area` |
| **Density** | 单元平均密度 | `StdCell Area / Free Placement Area`（= Core - Macro - Halo） |
| **Target Density** | placement 工具的目标密度 | 通常 0.65~0.80，越低越容易收敛时序 |

**为什么不能 100%？**
- 需要 **Routing 资源预留**（track space）
- 需要 **DRC 间距缓冲**（PG 走线、Shielding、Spare Cells）
- 需要 **CTolerance**（placement 算法的迭代缓冲）

> **实战经验**：7nm 先进工艺 core utilization 通常 ≤ 0.70；成熟工艺（28nm/40nm）可以到 0.75~0.80。

### 1.2 拥塞（Congestion）

**定义**：局部区域 routing track 需求 > 供应。

**两个层次**：
- **Global Routing Congestion**：全局规划阶段的拥塞图（GRC），按 GCell（粗粒度方格，如 1μm × 1μm）统计 demand vs supply
- **Detail Routing Congestion**：实际布线后的 short/via spacing 违例

**拥塞成因 Top 5**：

| # | 原因 | 占比 | 修复方向 |
|---|---|---|---|
| 1 | **Macro 摆放不当**（出 pin 一侧堵死） | 30% | 调整宏位置、留 Channel |
| 2 | **Pin 密度过高**（数据流汇聚） | 20% | 调整 floorplan、加 Buffer |
| 3 | **Logic 局部拥塞** | 20% | 微调 block size、Instance 间距 |
| 4 | **PG 走线占资源** | 15% | PG strap/ring 走顶层厚金属（M7/M8/AP），避免占用 M1~M3 的信号资源 |
| 5 | **Track 资源不足**（层数少、宽度窄） | 15% | 工艺层选择、PG 优化 |

### 1.3 CR（Critical Route / Congestion Relief）

工具用 **CR ratio** = demand / supply 评估风险：
- CR < 0.6：安全
- 0.6 ~ 0.8：黄色，需关注
- 0.8 ~ 1.0：红色，可能 DRC 违例
- CR > 1.0：必有问题，需要 floorplan 调整

## 二、12 道高频面试题

### 题 1：解释 Core Utilization、Floorplan Utilization、Density 三者的区别

**参考答案**：

| 指标 | 分子 | 分母 | 适用场景 |
|---|---|---|---|
| Core Util | StdCell Area | Core Area | 报告里最常见的数字 |
| Floorplan Util | StdCell + Macro + Halo | Core Area | floorplan 评审 |
| Density | StdCell | Core - Macro - Halo（可用空间） | placement 阶段 |

**关键差异**：Floorplan Util 高，**但 Density 也高** → 说明宏之间塞得满；**Floorplan Util 高、但 Density 低** → 说明宏多、剩余空间分散，placement 仍能跑。

**加分点**：
- 提到 "在 Innovus 里 `report_placement_utilization` 看到的 utilization 默认是 floorplan 概念"
- 解释 "为什么 Density 比 Core Util 更能反映 placement 难度"——因为 placer 看的是可用空间
- 7nm 工艺下 Density 通常不超过 0.75，否则 timing 收敛困难

---

### 题 2：Macro 摆放的"Pin Side 原则"是什么？为什么重要？

**参考答案**：

**原则**：把宏的 Pin 边朝向你**预期信号流出的方向**（一般是 Core 内部），不要朝向 die 边缘或被 blockage 堵死的那一侧。

**原因**：
- Macro 的 pin 出线方向决定了其周围 routing 资源的"排水方向"
- 如果 pin 朝着 channel（窄通道）出去，必然拥塞
- 如果 pin 朝着 die 边缘，那 1-2mm 内的 std cell 想连进来，必须绕远

**反面案例**：
```
      ┌──────────────┐
      │              │
      │   Macro 1    │  ← pin 朝右（被 Macro 2 堵住）
      │              │
      ├──────────────┤
      │   Macro 2    │
      └──────────────┘
```
Macro 1 的信号全堆在 Macro 1 与 Macro 2 之间 50μm 宽的 channel，必然 CR > 1.0。

**正面做法**：
- 同一功能模块的宏**保持 pin 方向一致**（如都朝上）
- 宏之间留 **Macro Spacing Rule × 1.5** 以上的通道
- 利用 **Channel Pattern** 提前规划好走线方向

**加分点**：
- 提到"先预估每个 macro 的 net count，乘以 0.5 估算 routing track 需求"
- 提到"宏多且 pin 复杂时，先做 macro plan 再做 floorplan，不要顺序颠倒"

---

### 题 3：什么是 Congestion Map？怎么读？

**参考答案**：

Congestion Map（拥塞图）是工具（Innovus / ICC2）生成的 2D 颜色图，横轴是 die 宽度，纵轴是 die 高度，每个 GCell 一个颜色：

| 颜色 | CR 区间 | 含义 |
|---|---|---|
| 蓝/绿 | < 0.5 | 富余 |
| 黄 | 0.5 ~ 0.7 | 正常 |
| 橙 | 0.7 ~ 0.85 | 警示 |
| 红 | 0.85 ~ 1.0 | 风险高、收敛代价大，需优先处理（不等于必然产生 DRC） |
| 黑 | > 1.0 | 必然出问题 |

**读图技巧**：
1. **看大片红色** → floorplan 错（如宏在中间堵死）
2. **看局部红色** → pin 密度高、fanout 扇出汇
3. **看红色条带** → 与 module boundary 重合 → RTL 拥塞，需 RTL 改写
4. **看红色沿 PG Rail** → PG 走线占资源

**加分点**：
- 提到"GRC（Global Route Congestion）在 placement 之前看，DRC 违例在 detail route 之后看"——两者时间线不同
- 提到"红色块 = 必出问题，黄色块 = 收敛时序代价大"

---

### 题 4：如何修复拥塞？按优先级排序你的修复策略

**参考答案**（按成本由低到高）：

| 优先级 | 修复手段 | 影响范围 | 成本 |
|---|---|---|---|
| P0 | 调 Density（增 Target Util）| 全局 | 极低（改命令） |
| P0 | 调整 PG 走线（高层化）| 全局 | 低 |
| P1 | 局部宏挪位 | 局部 | 中 |
| P1 | 加 Spare Cells/Endcap | 局部 | 低 |
| P1 | partial blockage / padding | 局部 | 低 |
| P2 | 改 Floorplan 拓扑 | 全局 | 中高 |
| P2 | 增 Routing Layer（多用 M3/M4）| 全局 | 中 |
| P3 | **RTL 改写**（加寄存器、pipeline）| 全局 | 极高 |
| P3 | **floorplan 大改** | 全局 | 极高 |

**核心原则**：
- 能用 placement / floorplan 解决的，不要动 RTL
- 红色条带与 block boundary 重合 → 必须动 RTL
- 调整前先看 congestion report，**别凭直觉**

**加分点**：
- 提到"在 Innovus 里 `specify_cell_pad` 或 `setPlaceMode -place_global_hold_strict` 可以局部加密"
- 提到"看 congestion 时同时看 timing——可能解决拥塞反而破坏了 timing"

### 题 5：什么是 Channel？什么样的宽度合适？

**参考答案**：

**Channel**（通道）是宏之间或宏与 edge 之间的可用走线区域。宽度计算公式：

```
Channel Width = max(
pin 走线需求（pin count × 每 pin 占 track 数）,
timing 关键路径走线资源,
spacing 规则保留,
工具算法迭代 buffer（×1.2）
)
```

**实战经验**：

| 场景 | 推荐 channel 宽度 |
|---|---|
| 宏之间、信号流密集 | 30~50μm（5x site） |
| 宏之间、信号稀疏 | 20~30μm |
| 宏与 Block Edge | 15~20μm |
| Memory 通道（数据流）| 50~80μm |
| 复杂 IP 之间 | 60~100μm |

**加分点**：
- 提到"channel 内尽量用高层金属（M3/M4）走线，避免占 M1/M2"
- 提到"过窄的 channel 是 CR > 1.0 的最常见原因"

---

### 题 6：什么是 Spare Cell？作用是什么？通常放多少？

**参考答案**：

**Spare Cell**（备用单元）是预先铺好的、未连接的标准单元（通常是 buffer/inverter/NAND）。作用：
- **ECO 用**：timing/DRC 修复时直接调用 spare cell 替换
- **DFT 用**：scan chain 调整时插入
- **功耗调节**：Vt swap
- **yield 提升**：替换缺陷单元

**常见数量**：
- 普通模块：1%~3% 的 std cell area
- 高 yield 要求模块：5%~10%
- 7nm 先进工艺：1% 起步（工艺贵）

**加分点**：
- 提到"spare cell 要在 placement 阶段就铺好，不能后期手动加"
- 提到"不同 cell 类型分别放一定比例（`eco_spare` / `decap_spare`）"
- 提到"`setPlaceMode -place_global_spare` 命令"

---

### 题 7：什么是 Endcap？Tap Cell？必须放吗？

**参考答案**：

| 类型 | 作用 | 工艺要求 |
|---|---|---|
| **Endcap** | 防止 std cell row 边缘的 poly/LVT 良率问题 | 几乎所有工艺都要求 |
| **Tap Cell** | 给衬底/阱提供 body tie（避免 latch-up） | 必须放 |
| **Decap** | 充当局部的电荷池，稳定电源 | 高频模块建议放 |
| **Well Tap** | 同 Tap Cell | — |

**Endcap 规则**：
- 每个 row 两端必须放 endcap
- 浮空的 row（中间无 cell）也要补
- 不同 Vt 的 row 之间要 boundary cell

**Tap Cell 规则**：
- 通常每 30~50μm 间隔一个
- 5nm/3nm 工艺对 latch-up 极敏感，间隔更小

**加分点**：
- 提到"现代工具会自动加这些 cell，但**漏放会 tapeout 后被 foundry 拒绝**"
- 提到"在 Innovus 里 `addEndCap` / `addWellTap` 命令"

---

### 题 8：什么是 Partial Blockage？和 Halo 的区别？

**参考答案**：

| 概念 | 含义 | 用途 |
|---|---|---|
| **Halo** | 宏周围的"排斥区域"，std cell 不会进 | 防止 std cell 靠宏太近，DRC/IR drop 风险 |
| **Blockage** | 完全禁止 std cell 放进去 | block 内无 std cell 区域（如 power 区域） |
| **Partial Blockage** | 按比例禁止 std cell（如 30% blockage 意思"放 70% 的 cell"） | 调节局部 density |

**实战场景**：
- 宏周围 5μm 放 halo（避免 std cell 贴在 macro 上）
- Memory 上方 10μm 放 blockage（因为 memory pin 走线要空间）
- 数据流汇聚区放 30% partial blockage 降低密度

**加分点**：
- 提到"`setPlaceBlockage` vs `setPartialBlockage` 区别"
- 提到"partial blockage 比完全 blockage 更平滑，但工具更难收敛"

---

### 题 9：如何判断是 Routing 拥塞还是 Placement 拥塞？

**参考答案**：

**Placement 拥塞**：标准单元密度高，但 routing 资源够
- 看 `report_placement_utilization`
- 看 `reportCongestion -hotSpot` 但 global route 没短路
- 修复：减 density / 改 floorplan

**Routing 拥塞**：density 正常，但走线资源不足
- 看 `reportCongestion` 在 detail route 之后 short 数
- 修复：加 routing layer、改 pin 层、shielding

**判断技巧**：
1. 先跑 `routeGlobal`，看 GRC
2. 如果 GRC 红但 DR 无 short → placement 阶段问题
3. 如果 GRC 黄但 DR 大量 short → routing 阶段问题

**加分点**：
- 提到"GRC 是全局布线的 demand/supply 预测（overflow），DRC 是实际几何规则违例——二者没有必然对应，GRC 红完全可能被 detail route 绕开或经 ECO 消化，是否真出问题以 DR 之后的 short/DRC 数为准"
- 提到"Innovus 里 `setOptMode -postRouteOpt ...` 用来 post-mask DR 的违例"

---

### 题 10：什么是 Blockage？Blockage 怎么影响 Placement？

**参考答案**：

Blockage 是工具在 placement 时**完全禁止**某些区域放 std cell 的标记：

- **`setPlaceBlockage`**：完全禁止
- **`setPartialBlockage`**：按比例禁止
- **`setSoftBlockage`**：尽量不放，必要时可破例

**Blockage 类型**：

| 类型 | 场景 |
|---|---|
| Routing Blockage | 阻止走线进入（如 PG 区域） |
| Placement Blockage | 阻止 cell 摆放 |
| Soft Blockage | placement 尽力避免，可破例 |
| Hard Blockage | 物理障碍（如 macro 内部） |

**关键点**：
- Blockage 面积算入"分母"还是"分子"？→ **不计入可用空间**（Innovus 里 blockage 区域不计入 std cell placement）
- Blockage 太大会导致 std cell 集中在小区域 → density 局部高 → 拥塞

**加分点**：
- 提到"blockage 不会自动给工具补偿——blockage 占的面积仍要算入 core area"
- 提到"用 blockage 模拟 'keep-out' 区域比 halo 灵活，但 halo 更稳"

---

### 题 11：为什么 Floorplan 阶段要留足够 Spacing？Spacing Rule 是什么？

**参考答案**：

**Spacing Rule** 是工艺厂规定的"宏与宏之间、宏与 cell 之间的最小距离"。

**Spacing 不够的后果**：
1. **DRC 违例**（如宏与 std cell 之间 poly spacing）
2. **PG 走线空间不足**（IR drop 风险）
3. **天线效应**（长走线累积电荷）
4. **Density 不收敛**（局部塞太满）

**典型 spacing 值**：

| 工艺节点 | Macro to Macro | Macro to Cell | Cell to Cell |
|---|---|---|---|
| 28nm | 5~10μm | 2~3μm | 0.1μm |
| 7nm | 8~15μm | 3~5μm | 0.05μm |
| 3nm | 10~20μm | 4~6μm | 0.03μm |

**加分点**：
- 提到"`LEF` 文件的 `MACRO` 定义里 `CLASS BLOCK` 的 spacing rule"
- 提到"在 Innovus 里 `setMacroSpacing` 可以额外加 padding"
- 提到"宏之间的 channel 太宽会浪费面积，太窄会拥塞——trade-off"

### 题 12：Floorplan 阶段如何预估 die size？

**参考答案**：

**die size 估算公式**：

```
Die Area = Core Area + IO Ring Area + Corner Cell Area
Core Area = Macro Area + Std Cell Area + Routing Area
     = (Sum of all Macro Area) / (1 - Std Cell Util%) × (1 + Channel%)
```

**估算步骤**：
1. **统计所有宏面积**：`sum of (macro_width × macro_height)`
2. **预估 std cell 数量**：从 RTL 综合报告 `report_area` 拿
3. **算 std cell 占用**：`std_cell_count × avg_cell_size`
4. **加 channel 比例**：根据宏密度预留 10%~30% 通道
5. **加 corner / power ring**：外圈 30~50μm
6. **乘 IO Ring 宽**：典型 100~200μm

**实战经验**：
- 宏占大头时，die size 主要看宏布局的"外接矩形"
- std cell 密度高时，预留 30% 通道给 routing
- IO 数量决定 die 周长，周长决定最小 die size

**加分点**：
- 提到"用 hierarchical floorplan 可以降低顶层 die size——子模块面积可叠加"
- 提到"die size 评估要 buffer 5%~10% 防止后期 macro 调整打回重做"
- 提到"硬 IP（PCIe/USB/SerDes）的尺寸通常是 floorplan 的硬约束"

## 三、综合题（开放题）

### 题 13：项目里遇到严重的拥塞问题，你怎么定位和解决？

**参考答案框架**：

1. **看现象**：
 - `reportCongestion` 看 CR map
 - `report_short` 看 DR 阶段违例
 - timing report 看 slack 是否变差

2. **定位原因**：
 - 红色在 macro 周围 → macro 摆放
 - 红色沿 module boundary → RTL 数据流
 - 红色密集在 IO 之间 → pin 分配问题

3. **修复策略（成本由低到高）**：
 - 调 PG 走线、调整 partial blockage
 - 局部 macro 挪位、加 spare cell
 - 调整 floorplan 拓扑
 - RTL 改写（pipeline 拆分 / 加寄存器 / 改架构）

4. **验证**：
 - 重跑 timing + DR + 拥塞
 - 确认修复后无回归

**加分点**：
- 提到"不能只看一张图——要分析 floorplan + congestion + timing + power 综合"
- 提到"修复拥塞常常会破坏 timing——必须同时看"
- 提到"`analyzeCongestion -connectivity` 看连通性，不只是 demand"

## 四、面试常见追问

| 面试官追问 | 你的应对 |
|---|---|
| "CR < 0.5 还担心拥塞吗？" | "还看分布：CR < 0.5 但全图均匀，可能有局部峰值" |
| "如果 floorplan 改完还拥塞呢？" | "那就看 RTL——加 pipeline 寄存器、改架构" |
| "Macro pin 全部朝里能解决问题吗？" | "部分解决——还要看 channel 宽、density" |
| "utilization 越高越好吗？" | "不，超过 0.75 后 timing/DR 收敛成本指数级上升" |
| "如果没有 congestion report 工具怎么办？" | "看 net count 分布、fanout 大值、pin density 估算" |

## 五、面试避坑

1. 把 "Core Utilization" 和 "Density" 混用——一定区分清楚
2. 说"100% utilization 也能做"——实际工艺会卡 DRC、timing
3. 提"拥塞只能改 RTL"——大部分情况 floorplan 调整足够
4. 答 floorplan 不提 timing 影响——floorplan 改后必须重跑 timing
5. 忘记 spare cell / endcap——这些是"必知必会"题

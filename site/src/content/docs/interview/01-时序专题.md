## 题 1（中频） | Setup Slack 公式

### 题目
请写出 Setup Slack 的完整公式，并解释每一项的含义。

### 参考答案

```
Setup Slack = T_period 
          + (Capture Clock Arrival Time) 
          - (Launch Clock Arrival Time) 
          - (Data Path Delay)
          - Setup Uncertainty
          - Setup Time of Capture FF
```

或者简化为：

```
Setup Slack = T_cycle - (T_clk2q + T_logic + T_net) - T_skew - T_setup - T_uncertainty
```

**每一项含义**：

| 项 | 含义 |
|---|---|
| `T_cycle` | 时钟周期（频率倒数） |
| `T_clk2q` | 源寄存器的 Clock-to-Q 延迟 |
| `T_logic` | 组合逻辑延迟（cell delay） |
| `T_net` | 线延迟（net delay） |
| `T_skew` | 时钟 Skew（Capture - Launch） |
| `T_setup` | 目标寄存器的 Setup 时间 |
| `T_uncertainty` | 时钟不确定性（jitter + margin） |

### 加分点
- 主动提到"Skew 对 Setup 的影响是双向的——Capture 早到时有助于 Setup"
- 提到 OCV derate："实际工程中，每一项还有 OCV 悲观系数"
- 提到 CPPR："共同时钟路径会被工具自动扣除悲观"

## 题 2（中频） | Hold Slack 公式

### 题目
请写出 Hold Slack 的完整公式，并说明 Hold 违例为什么与时钟周期无关。

### 参考答案

```
Hold Slack = (Data Path Delay)
         - (Capture Clock Arrival Time - Launch Clock Arrival Time)
         - Hold Uncertainty
         - Hold Time of Capture FF
```

或者简化为：

```
Hold Slack = (T_clk2q + T_logic + T_net) - T_skew - T_hold - T_uncertainty
```

**Hold 与周期无关的原因**：
- 数据路径延迟**不依赖于时钟周期**
- Hold 检查的是"最短路径"——下一拍时钟沿到达时，数据是否已经被锁住
- 即使时钟周期很长（1 ms），如果数据路径只有 100 ps，依然 Hold 违例

### 加分点
- 主动区分 Setup/Hold 的本质："Setup 是**频率问题**，Hold 是**制造/设计问题**"
- 提到 FF corner："Hold 违例最容易在 FF corner 暴露，因为 cell 延迟变小"
- 提到时序例外："Multi-cycle path 的 hold 必须配对设 N-1"

## 题 3（较高频） | OCV、CPPR、AOCV、POCV 的关系

### 题目
请解释 OCV 是什么，CPPR 为什么需要它，AOCV/POCV 又解决了 OCV 的什么问题。

### 参考答案

#### OCV (On-Chip Variation)
- 同一颗芯片上不同位置的 Cell 因制造工艺偏差，延迟不同
- 芯片中心 vs 边缘，密度差异 → 速度差异
- **保守做法**：对所有数据路径加 +5% derate，对所有时钟路径加 -5% derate

**问题**：过于悲观——把不该悲观的路径也悲观了。

#### CPPR (Clock Path Pessimism Removal)
- Launch 和 Capture 共享时钟路径时，OCV derate 被算了两次
- 实际对 Skew 没贡献
- 工具识别共享段，**扣除重复计算的悲观性**

#### AOCV (Advanced OCV)
- OCV 是**固定 derate**（路径深度无关）
- AOCV 根据**路径深度**和**物理距离**分级 derate
- 路径越深，OCV 越小（统计平均）

#### POCV (Parametric OCV)
- AOCV 仍是 deterministic
- POCV 把 Cell 延迟建模成正态分布
- 用 **σ（标准差）** 而非固定 derate
- 7nm 及更先进工艺必须用

### 加分点
- 主动给出例子："比如 7nm 工艺，PT 默认 AOCV/POCV 模式"
- 提到"为什么 AOCV 比 OCV 准"：路径越长，统计平均 → 波动越小
- 提到 SOCV（Statistical OCV）：与 POCV 类似，Siemens EDA 的叫法

## 题 4（中频） | 修复 Setup 违例的 5 种方法

### 题目
Setup 违例了，你有哪些修复策略？按优先级排序。

### 参考答案

| 优先级 | 方法 | 适用场景 |
|---|---|---|
| **P1** | 调整 CTS / Useful Skew | 时钟裕量在两寄存器间分布不均 |
| **P2** | 改 Cell 驱动强度 | 关键路径在某一级驱动弱 |
| **P3** | 插入 Buffer | 长 net 驱动能力不足 |
| **P4** | Vt Swap（LVT → HVT）| LVT cell 快但漏电大；改 HVT 减功耗但 setup 更差 |
| **P5** | 改 Cell 类型（AND → NAND）| 复杂门重组 |
| **P6** | 改 RTL / Pipeline | 路径太长，无法局部修复 |
| **P7** | 降频（增加 cycle）| 兜底方案 |

**修复原则**：
- **先局部后全局**——能不动的就不动
- **先改时钟后改逻辑**——useful skew 是最便宜的
- **优先 P1-P5**——这些是后端能改的；P6/P7 是设计问题

### 加分点
- 提到"实际项目里，P1+P2+P3 解决 90% 的 setup 问题"
- 提到"Pipeline 切割会改 RTL，需要提前和前端对齐"

## 题 5（中频） | 修复 Hold 违例的 5 种方法

### 题目
Hold 违例了，你有哪些修复策略？Setup 和 Hold 的修复方法有什么区别？

### 参考答案

| 方法 | 做法 | 适用场景 |
|---|---|---|
| **P1** | 数据路径加 Delay Cell / Buffer | 数据路径太短 |
| **P2** | 降低驱动强度（X4 → X2） | 数据路径太短 |
| **P3** | 改 Cell 类型（换成慢 Cell） | 单 Cell 延迟太小 |
| **P4** | Useful Skew：让 Capture 时钟早到，或让 Launch 时钟晚到 | CTS 之后、skew 可调度 |
| **P5** | 修复 CTS（缩短 Capture 时钟延迟） | CTS 不平衡 |

**与 Setup 修复的本质区别**：

| 维度 | Setup 修复 | Hold 修复 |
|---|---|---|
| 本质 | 让数据跑得**更快** | 让数据跑得**更慢** |
| 难度 | 较易（工具自动优化） | 必须**人工 + 工具结合** |
| 时机 | Pre-CTS 就要收敛，Post-CTS 复核 | Post-CTS 才准，Pre-CTS 不追求全清 |
| 频率敏感 | 敏感 | 不敏感 |
| 主要矛盾 | 频率 vs 延迟 | Skew vs 制造 corner |

### 加分点
- 提到"Hold 违例在 Sign-off 前必须全清，但 Pre-CTS 阶段不追求全清"
- 提到"FF corner 是 Hold 杀手，必须看 FF 下的 slack"

### 常见错误答法（本题最容易翻车的地方）

**错误说法**："Pre-CTS 是 ideal clock、skew=0，所以 Pre-CTS 一定要把 Hold 修干净。"

这句话在面试里说出来会直接被扣分，有三个原因：

**第一，Pre-CTS 的 Hold 数字本身就是假的。** 时钟是理想的，skew 恒等于 0，你看到的 Hold 违例全部来自"数据路径太短"。CTS 之后真实 skew 出现，一部分违例会被 skew 自然抵消，一部分会变得更严重——数字全变了，现在修等于对着假靶子打。

**第二，修 Hold 的动作会 1:1 吃掉 Setup 余量。** 修 Hold 只有一条路：给数据路径加延迟（插 buffer / delay cell、降驱动强度、换慢 cell）。数据路径延迟增加 Δ，Setup slack 就减少 Δ。Pre-CTS 修得越狠，Post-CTS 的 Setup 越难收敛——这正是"CTS 之后 setup 烂"最常见的成因，而且排查时最难想到，因为违例路径上那一串 buffer 看起来是"正常优化"。

**第三，skew 是可以用来修 Hold 的资源，但你得先有时钟树。** 约定 skew = T_capture − T_launch，则：

```
Hold slack  = T_data_path − T_hold − skew
Setup slack = T_period − T_setup − T_data_path + skew
```

skew 为负（Capture 时钟比 Launch 早到）时 Hold slack 变大；CTS 的 useful skew 调度还能主动制造这种负 skew 去救 Hold。Pre-CTS 没有时钟树，也就没有这把工具可用。

**正确答法**：

| 阶段 | Setup | Hold |
|---|---|---|
| Pre-CTS | **收敛**。Setup 主要由数据路径决定，ideal clock 下估算已够用，且越往后能动的余地越小 | **不追求 clean**。只处理大到 skew 兜不住的违例，或用 hold uncertainty 把预期 post-CTS skew 建模进去 |
| Post-CTS | 复核真实 skew 下的结果 | **开始修**，此时数字准确 |
| Post-Route / Sign-off | 收尾 ECO | **必须全清** |

**这不是绝对**——如果某个 Hold 违例大到后续 ECO 补不回来，或者涉及 scan chain 的 shift-mode Hold，Pre-CTS 提前处理是合理的。准确的说法是"不追求 clean"，不是"绝对不动"。

**一句话**：Setup 早修，Hold 晚修。Pre-CTS 追求 Hold clean 是拿 Setup 换一个还没算准的数字。

## 题 6（较高频） | False Path vs Multi-Cycle Path

### 题目
解释 False Path 和 Multi-Cycle Path 的区别，分别举例说明。

### 参考答案

| 维度 | False Path | Multi-Cycle Path |
|---|---|---|
| **含义** | 工具不分析（功能上不会触发） | 工具按多周期分析 |
| **示例** | 不同时钟域、测试模式专用路径 | 慢速总线（数据 4 个周期更新） |
| **Setup 检查** | 不检查 | 按 N 周期检查 |
| **Hold 检查** | 不检查 | 按 N-1 周期检查 |
| **Tcl 命令** | `set_false_path` | `set_multicycle_path N -setup` |

**关键提醒**：
- 设了 Multi-Cycle Setup **必须同时设 Hold N-1**——否则 hold 用 0 周期检查，必然违例

```tcl
# 正确写法
set_multicycle_path 4 -setup -from [get_pins A/CLK] -to [get_pins B/D]
set_multicycle_path 3 -hold  -from [get_pins A/CLK] -to [get_pins B/D]
```

### 加分点
- 给出真实场景："我之前做 USB，USB 复位寄存器到状态机的路径是 false path"
- 提到"sdc 里要把 false path / MCP 分清楚，否则 hold 全炸"

## 题 7（较高频） | 时钟 Skew 与 OCV 共同影响 Setup/Hold

### 题目
请说明时钟 Skew 对 Setup 和 Hold 分别有什么影响，并解释为什么。

### 参考答案

#### 对 Setup 的影响
```
Setup Slack 增加 ⇔ Capture 时钟晚到（Skew 正向）
Setup Slack 减少 ⇔ Capture 时钟早到（Skew 负向）
```

**直观理解**：Capture 窗口晚 → 数据有更多时间到达 → Setup 更宽裕。

#### 对 Hold 的影响
```
Hold Slack 减少 ⇔ Capture 时钟晚到（Skew 正向）  
Hold Slack 增加 ⇔ Capture 时钟早到（Skew 负向）
```

**直观理解**：Capture 窗口晚 → 数据刚到就被"立刻"采样 → Hold 可能不够。

#### 工程意义
- **Setup 紧张 → 想 Skew 让 Capture 晚到**（useful skew）
- **Hold 紧张 → 想 Skew 让 Capture 早到**

**但这是矛盾的**！一个芯片不可能同时让所有路径偏向 Setup 或 Hold。这就是 CTS 的艺术——**找到全局最优 Skew 分布**。

### 加分点
- 提到"OCV 让 Skew 不确定，Skew 偏差直接影响 Hold margin"
- 提到"Pre-CTS 是 ideal clock、skew=0，Hold 数字不可信，所以 Hold 留到 Post-CTS 修——这是本题最大的加分点，也是最多人答反的地方"

## 题 8（高频） | Setup 检查的具体例子

### 题目
时钟周期 10 ns，Launch FF 到 Capture FF 之间的延迟总和（包括 cell + net + clk2q + setup time）是 7 ns。Capture FF 的时钟比 Launch FF 晚到 0.5 ns。Setup Uncertainty 是 0.2 ns。求 Setup Slack。

### 参考答案

```
Setup Slack = T_period + T_skew - T_data_path - T_setup - T_uncertainty
          = 10 + 0.5 - 7 - 0 - 0.2
          = 3.3 ns
```

> 注意：题目说"延迟总和已包含 setup time"，所以公式里的 T_setup 取 0。

**判定**：Slack = 3.3 ns > 0 → **Setup 满足**

如果延迟总和是 11 ns 而不是 7 ns：
```
Setup Slack = 10 + 0.5 - 11 - 0.2 = -0.7 ns
```
→ **Setup 违例 0.7 ns**，需要修复

### 加分点
- 主动分析"违例的话怎么修"：增大 cycle / 改 cell / 改 RTL

## 题 9（较高频） | Timing Sign-off 包含哪些检查？

### 题目
Timing Sign-off 需要跑哪些 corner / mode？完整列举。

### 参考答案

#### Mode（工作模式）
1. **Function Mode** — 正常功能模式
2. **Scan Mode** — DFT scan shift
3. **BIST Mode** — 内建自检（mbist / lbist）
4. **Sleep Mode** — 低功耗模式
5. **Wakeup Mode** — 唤醒模式
6. **Mission Mode** — 应用场景（不同 PVT）

#### Corner（PVT）
1. **SS**（Slow NMOS + Slow PMOS, Low VDD, High T）— Setup 最差
2. **FF**（Fast NMOS + Fast PMOS, High VDD, Low T）— Hold 最差
3. **TT**（Typical, Nominal VDD, 25°C）— 典型
4. **SF**（Slow NMOS + Fast PMOS, High VDD, Low T）— Hold 检查
5. **FS**（Fast NMOS + Slow PMOS, Low VDD, High T）— Setup 检查

#### 全组合
例如 `6 mode × 5 corner = 30` 个组合，工具全跑。

**额外检查**：
- AOCV / POCV 模式
- SI（Crosstalk）分析
- 多个 timing scenario（multi-mode multi-corner, MMMC）
- Hold fix 的 systematic margin

### 加分点
- 提到"实际项目里，会拆成 scenarios，每个 scenario 是 mode × corner 子集"
- 提到"sign-off clean 的标准是所有 scenario 下所有 setup/hold slack ≥ 0"

## 题 10（高频） | 现场分析：一个真实违例场景

### 题目
你的项目里，同一个模块 a5 和 a10 之间有一条路径：
- 时钟周期 10 ns
- 数据路径延迟（cell + net）7 ns
- T_clk2q = 0.2 ns
- T_setup = 0.1 ns
- T_hold = 0.05 ns
- T_skew = 0.3 ns（Capture 晚于 Launch）
- Uncertainty = 0.2 ns
- OCV derate：数据 +5%，时钟 -5%

问：
1. Setup Slack 是多少？
2. Hold Slack 是多少？
3. 如果 Setup 违例 0.5 ns，你会怎么修？

### 参考答案

#### (1) Setup Slack（含 OCV）

```
T_data_ocv = (T_clk2q + T_logic + T_net) × 1.05
         = 7.2 × 1.05
         = 7.56 ns

T_skew_ocv = T_skew × 0.95
         = 0.3 × 0.95
         = 0.285 ns

Setup Slack = T_period + T_skew_ocv - T_data_ocv - T_setup - T_uncertainty
          = 10 + 0.285 - 7.56 - 0.1 - 0.2
          = 2.425 ns
```

> **Setup 满足**（Slack > 0）

#### (2) Hold Slack（含 OCV）

```
T_data_ocv = 7.2 × 0.95 = 6.84 ns   # Hold 检查数据路径更快
T_skew_ocv = 0.3 × 1.05 = 0.315 ns    # Hold 检查时钟更悲观

Hold Slack = T_data_ocv - T_skew_ocv - T_hold - T_uncertainty
         = 6.84 - 0.315 - 0.05 - 0.2
         = 6.275 ns
```

> **Hold 满足**（Slack > 0）

#### (3) 如果 Setup 违例 0.5 ns

修复策略（按优先级）：
1. **Useful skew**：调整 CTS 让 Capture 晚到 0.5 ns（注意：这会牺牲其他路径）
2. **Cell 升级**：把关键路径上的 X2 驱动改 X4
3. **Buffer 插入**：长 net 加 buffer
4. **Vt swap**：LVT → HVT 慢但漏电小 → 反过来不行（HVT 更慢）；改 NVT 或 LVT 更快
5. **Pipeline 切割**：如果关键路径过长，需改 RTL

**实际选择**：优先 (1) 和 (2)，不动 RTL。

### 加分点
- OCV derate 的方向记错：Setup 用 +5%/−5%，Hold 用 0.95/1.05（反过来）
- 提到"CPPR 如果存在，要扣除共享时钟段"

# 内容来源与勘误记录

这一页回答两个问题：这些内容是怎么来的，以及已经错了哪些。

---

## 1. 这些内容是怎么来的

先说清楚，免得误用。

**本站内容由 AI 辅助生成**，基于大模型的领域知识整理而成，写作流程是：确定选题与大纲 → 生成正文 → 人工通读校对 → 发现错误后修正并记录。

几个必须知道的事实：

- **没有逐条引用出处。** 文章里出现的工具命令、参数量级、经验数字来自通用工程常识，不是从某一本书或某一份文档里抄过来的具体页码。需要精确数值时不要直接引用本站。
- **未经资深工程师逐条审校。** 维护者是个人，没有做过完整的行业评审。已发现的错误会公开记录（见第 4 节），但**没有被发现的错误一定存在**。
- **工具命令以所用版本为准。** EDA 工具的选项名和默认行为随版本变化，本站给出的命令是通用写法，跑之前对照你手上的 User Guide 确认。
- **公司相关的流程差异很大。** 不同公司、不同工艺节点、不同 foundry 的 flow 差别可以非常大。本站讲的是通行做法，不是你入职后要遵守的那份 flow doc。

**怎么用比较安全**：

1. 用它建立知识框架和面试话术，这部分的可靠性最高。
2. 遇到具体数字（利用率百分比、skew 目标值、违例阈值），一定要拿你项目的实际数据或者官方文档复核。
3. 面试里被追问时，说"我理解通行做法是 X，具体要看工艺和 flow"比背一个死数字稳得多。
4. 发现错误请提交勘误，见第 5 节。

## 3. 本站在哪些地方最容易出错

按经验排序，越靠前越要留个心眼：

1. **具体数值门槛**（"utilization 一般 70%~80%""skew 控制在 100 ps 以内"）——量级是对的，具体数字随工艺和项目变。
2. **工具命令与选项名**——版本差异大，且各家公司脚本里包了一层自己的封装。
3. **流程顺序的"必须"**——实际 flow 里很多步骤是可配置的、可跳过的，本站写得偏绝对。
4. **公司招聘信息**——岗位表来自公开渠道汇总，投递前务必以官方渠道为准。

## 4. 勘误记录

已确认并修正的错误，公开留档。

### 2026-10-17 · Pre-CTS 是否应该修 Hold

**错误原文**（出现在三处）：

- `基础知识 / 布局布线 PNR`：「Pre-CTS 必须 Hold clean——否则后续 CTS 崩溃」
- `八股题库 / 时序专题`：「Pre-CTS 假设 ideal clock（skew=0），所以 Pre-CTS 一定要 hold clean」
- `八股题库 / 时序专题`：Setup/Hold 对比表中的「时机：Pre-CTS 就必须修」

**为什么错**：

1. Pre-CTS 时钟是 ideal 的，skew 恒为 0，此时报告的 Hold 违例全部来自"数据路径太短"。CTS 之后真实 skew 出现，这些数字会被改写，在其中修等于对着错误的靶子做优化。
2. 修 Hold 的唯一手段是给数据路径加延迟（插 buffer / delay cell、降驱动、换慢 cell），数据路径延迟增加 Δ，Setup slack 就 1:1 减少 Δ。Pre-CTS 修得越狠，Post-CTS 的 Setup 越难收敛。
3. 负 skew（Capture 时钟比 Launch 早到）会天然改善 Hold，CTS 的 useful skew 调度还能主动利用这一点。Pre-CTS 没有时钟树，也就没有这个资源。

**修正后的说法**：

- Setup 在 Pre-CTS 收敛，Hold 在 Post-CTS / Post-Route 才全清。
- Pre-CTS 不追求 Hold clean；只处理大到 skew 兜不住的违例，或者用 hold uncertainty 把预期的 post-CTS skew 建模进去。
- 例外：量级大到后续 ECO 补不回来的违例、scan chain 的 shift-mode Hold，可以在 Pre-CTS 提前处理。

**修正位置**：`02-时钟树综合 CTS` 新增 Q5；`04-布局布线 PNR` 修正第 9 节实战建议与流程表；`01-时序专题` 题 5 后新增「常见错误答法」小节。

**感谢**：由读者在技术社区指出。

### 2026-10-17 · 用 Useful Skew 修 Hold 的方向写反了

**错误原文**：`八股题库 / 时序专题` 题 5：「P4：Useful Skew（让 Capture 时钟晚到）」。

**为什么错**：约定 skew = T_capture − T_launch，Hold slack = T_data − T_hold − skew。让 Capture 时钟**晚到**会让 skew 变正、Hold slack 变小，方向正好相反——那是修 Setup 的做法。

**修正后的说法**：修 Hold 的 useful skew 是让 Capture 时钟**早到**（或让 Launch 时钟晚到），使 skew 为负。

## 5. 怎么提交勘误

三种方式任选：

1. **GitHub Issue**：在仓库 `2buhtig123/backend-kb` 提 issue，标题写清文章名和位置。
2. **Pull Request**：直接改 `site/src/content/docs/` 下对应的 Markdown 文件，一并更新本页的勘误记录。
3. **邮件 / 私信**：不方便开 GitHub 的话，把「文章名 + 原文引用 + 你认为正确的说法 + 依据」发过来即可。

提交时最好带上依据（官方文档、书本页码、或者你项目里的实测数据）。没有依据的质疑也欢迎，只是处理优先级会低一些——被采纳的勘误会记名致谢，除非你要求匿名。
